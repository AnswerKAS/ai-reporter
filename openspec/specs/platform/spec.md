# platform Specification

## Purpose
Возможность описывает исполняемую платформу системы: состав FastAPI-приложения, метабазу PostgreSQL со схемой приложения, конфигурацию через `.env`, фоновый воркер, восстановление после сбоев и порядок доставки на сервер.

## Requirements

### Requirement: Состав приложения
Бэкенд SHALL быть одним FastAPI-приложением (`app.main`), собранным из роутеров `auth`, `reports`, `datasets`, `semantic`, `admin`, с префиксом `/api` и открытой проверкой живости `GET /api/health`. Код SHALL быть разложен по пакетам: `core/` (конфигурация, метабаза, безопасность), `schemas/` (Pydantic-контракты), `api/` (роутеры), `services/` (хранилище артефактов, фоновая уборка), `datasets/` (реестр и адаптеры источников), `semantic/` (словарь метрик и разрезов), `query/` (построитель SQL, диалекты, разбор описаний), `reports/` (исполнитель определений, витрина, сиды).

#### Scenario: Проверка живости
- **WHEN** клиент запрашивает `GET /api/health` без токена
- **THEN** сервис отвечает `{"status": "ok"}`

#### Scenario: Запуск приложения
- **WHEN** приложение стартует
- **THEN** в lifespan выполняются: создание схемы и таблиц, разовая миграция из legacy-SQLite, создание дефолтного администратора, регистрация дефолтных датасетов и запуск фоновой уборки

### Requirement: Метабаза приложения
Все данные приложения (отчёты с их определениями, пользователи, группы, доступы, сессии, датасеты, метрики, разрезы, связи, служебные ключи) SHALL храниться в PostgreSQL в отдельной схеме (`PG_SCHEMA`, по умолчанию `ai_reporter`); `search_path` выставляется на каждом соединении. Схема и таблицы SHALL создаваться идемпотентно при старте (`CREATE TABLE IF NOT EXISTS`), а изменения существующих таблиц — идемпотентными `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`.

#### Scenario: Первый старт на пустой базе
- **WHEN** приложение стартует на базе, где схемы приложения ещё нет
- **THEN** схема и все таблицы создаются, приложение работает без ручных миграций

#### Scenario: Старт на базе предыдущей версии
- **WHEN** приложение стартует на базе, где ещё есть таблица черновиков скиллов и колонки отчёта на скиллах
- **THEN** миграция удаляет отчёты, которые исполнять больше нечем, вместе с их доступами и файлами, снимает таблицу черновиков и лишние колонки

### Requirement: Устойчивость соединений с метабазой
Работа с PostgreSQL SHALL идти через пул соединений с проверкой живости при выдаче (`check_connection`), коротким `max_idle` и `min_size=0`; при недоступности пула система SHALL переходить на прямые подключения с повторными попытками. Синхронные обращения к базе из async-обработчиков SHALL выполняться через пул потоков, чтобы одна медленная операция не блокировала весь процесс.

#### Scenario: Сеть рвёт простаивающие соединения
- **WHEN** соединение в пуле разорвано сетью между запросами
- **THEN** проверка живости при выдаче отбраковывает его, запрос выполняется на здоровом соединении

#### Scenario: Пул недоступен
- **WHEN** пул не удалось создать
- **THEN** система логирует это один раз и продолжает работать прямыми подключениями с тремя попытками

### Requirement: Разовая миграция из legacy-SQLite
При первом старте система SHALL переносить данные из устаревшего файла `backend/reports.db` в PostgreSQL и отмечать факт миграции в служебной таблице, чтобы перенос не повторялся.

#### Scenario: Повторный старт после миграции
- **WHEN** приложение перезапускается после успешной миграции
- **THEN** повторный перенос не выполняется, данные PostgreSQL остаются авторитетными

### Requirement: Конфигурация через .env
Настройки SHALL читаться из `backend/.env` и окружения процесса без правки кода. После миграции все подключения приложения к БД SHALL задаваться именованными записями одной JSON-переменной `DB_CONNECTIONS`: `metabase` задаёт PostgreSQL метабазы и её схему, `demo` — демо-витрину, остальные ключи — источники датасетов. Если JSON задан, неверный формат или отсутствие `metabase` SHALL останавливать запуск. Для старой установки до разовой миграции прежние `PG*`, `DATABASE_URL` и DSN датасетов SHALL читаться ради совместимости. Остальные настройки SHALL оставаться отдельными переменными: `INTERPRET_*`, `CHAT_*`, `OPENROUTER_*`, `ARTIFACTS_*`, `SESSION_TTL_DAYS` и `CORS_ORIGINS`. DSN ClickHouse SHALL корректно разбирать пароль со спецсимволами.

#### Scenario: Пароль ClickHouse со спецсимволами
- **WHEN** пароль в `DB_CONNECTIONS.demo.dsn` содержит `@`
- **THEN** он разбирается корректно без смешения с именем сервера

#### Scenario: Фронт на другом домене
- **WHEN** оператор задаёт `CORS_ORIGINS` со списком адресов
- **THEN** браузерные запросы с этих адресов проходят CORS

#### Scenario: Неверный JSON
- **WHEN** `DB_CONNECTIONS` содержит некорректный JSON
- **THEN** запуск завершается понятной ошибкой без раскрытия секретов

### Requirement: Фоновая уборка
Система SHALL держать один фоновый цикл, который периодически удаляет просроченные сессии и переживает сбои базы и сети без остановки. Никакой другой фоновой работы у приложения нет: отчёты считаются в момент запроса.

#### Scenario: Сбой базы во время уборки
- **WHEN** обращение к базе внутри цикла падает с ошибкой
- **THEN** цикл логирует ошибку, ждёт минуту и продолжает работу

#### Scenario: Просроченные сессии
- **WHEN** в таблице сессий есть записи старше срока жизни
- **THEN** очередная уборка удаляет их и сообщает количество в лог

### Requirement: Доставка на сервер
После каждого push в `main` GitHub Actions SHALL проверять тесты бэкенда,
lint и сборку фронтенда и валидность OpenSpec. Сервис в LXC 111 SHALL
доставлять только точный коммит `main`, для которого соответствующий workflow
события `push` завершился успешно. Доставка SHALL сохранять серверные `.env`,
Docker-тома и загруженные артефакты, проверять `/api/health` и восстанавливать
предыдущий исходный код при ошибке. GitHub Actions не требует доступа к
приватной сети Proxmox или секретов сервера.

#### Scenario: Проверки не прошли
- **WHEN** workflow завершился неуспешно или ещё идёт
- **THEN** сервер не доставляет этот коммит

#### Scenario: Успешный push в main
- **WHEN** workflow события push для текущего SHA main завершился успешно
- **THEN** сервер обновляет backend и frontend, не изменяя Langfuse и данные

#### Scenario: Загруженные данные на сервере
- **WHEN** выполняется доставка новой версии
- **THEN** файлы `.env`, Docker-тома и загруженные CSV остаются на месте

#### Scenario: Неуспешная новая версия
- **WHEN** сборка или проверка здоровья завершается ошибкой
- **THEN** сервер восстанавливает предыдущий исходный код и сообщает ошибку

### Requirement: Локальный Langfuse
Проект SHALL предоставлять отдельный Docker Compose для Langfuse с постоянными томами и секретами вне Git. Подключение бэкенда SHALL задаваться переменными `LANGFUSE_*` и быть опциональным.

#### Scenario: Локальный запуск
- **WHEN** оператор запускает Compose Langfuse с локальным файлом секретов
- **THEN** web и API Langfuse становятся доступны, а данные переживают перезапуск контейнеров

### Requirement: Корректное завершение текущих ответов при обновлении
Контейнеры backend и frontend SHALL получать до 10 минут для завершения активных соединений при штатном обновлении Compose. Внутренний nginx SHALL передавать запрет буферизации внешнему прокси и SHALL не буферизовать или сжимать поток API.

#### Scenario: Обновление во время анализа
- **WHEN** обновление останавливает контейнер с активным ответом агента
- **THEN** Compose ожидает его корректного завершения до 10 минут вместо принудительного завершения через 10 секунд

### Requirement: Откат неуспешной операции в пуле
Контекст соединения из пула SHALL получать исключение вызывающего кода и откатывать неуспешную транзакцию вместо фиксации частичных изменений, включая замену назначений доступа.

#### Scenario: Ошибка после записи назначения
- **WHEN** атомарная операция записала часть назначений и завершилась исключением
- **THEN** пул откатывает изменения и возвращает соединение без частично сохранённой операции
