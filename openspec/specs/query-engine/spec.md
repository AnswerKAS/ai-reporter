# query-engine Specification

## Purpose
Возможность описывает построитель запросов: превращение секции отчёта (набор метрик, разрезов, фильтров) в один SQL-запрос к источнику, планирование джойнов по связям, защиту от размножения строк и от произвольного SQL со стороны пользователя, а также перевод ошибок источника на язык того, кто SQL не пишет.

## Requirements

### Requirement: Сборка SQL из выверенных определений
Весь SQL секции SHALL собираться построителем из определений семантического слоя и полей, сверенных со схемой датасета. Пользовательские значения (значения фильтров) SHALL попадать в запрос только параметрами диалекта, никогда — конкатенацией. Произвольный SQL от пользователя SHALL быть невозможен по построению.

#### Scenario: Значение фильтра с кавычками
- **WHEN** пользователь применяет фильтр со значением, содержащим кавычки и SQL-фрагмент
- **THEN** значение уходит параметром, запрос выполняется корректно, инъекция невозможна

#### Scenario: Метрики и разрезы секции неизвестны словарю
- **WHEN** определение ссылается на slug, которого нет ни в словаре, ни среди полей отчёта
- **THEN** сборка секции отклоняется с перечнем неизвестных имён до обращения к источнику

### Requirement: Диалекты источников
Построитель SHALL учитывать различия источников через диалект: цитирование идентификаторов, усечение дат по гранулярности, синтаксис параметров, настройки, необходимые для корректного FULL JOIN, **синтаксис ограничения выдачи** (`LIMIT`/`OFFSET` против `OFFSET … ROWS FETCH FIRST … ROWS ONLY`) и **форму алиаса производной таблицы** (с `AS` или без него). Ни одна из этих конструкций SHALL не собираться в построителе в обход диалекта. Поддерживаются `clickhouse`, `postgres` и `oracle`; для источника без диалекта (например CSV) секция SHALL отклоняться с явным сообщением, а не собираться неверно.

Диалект Oracle SHALL усекать даты через `TRUNC` (неделя — по ISO, с понедельника), передавать значения именованными привязками `:имя`, приводить границы периода через `TO_DATE(:имя, 'YYYY-MM-DD')` и ограничивать выдачу конструкцией `OFFSET … ROWS FETCH FIRST … ROWS ONLY`, где `OFFSET` стоит перед `FETCH`. Алиас производной таблицы SHALL записываться без `AS`.

Поддерживаемая версия Oracle — **12.2 и новее**: алиасы выдачи построителя (`m_<slug>`, `d_<slug>`) при длинном slug'е превышают предел идентификатора в 30 байт, действовавший до 12.2.

#### Scenario: Гранулярность по неделям в ClickHouse
- **WHEN** секция строится по разрезу типа `date` с гранулярностью `week` на ClickHouse
- **THEN** дата усекается функцией источника и приводится к дате, график получает точки по неделям

#### Scenario: Ограничение выдачи в Oracle
- **WHEN** секция по oracle-датасету собирается с ограничением строк, а детализация запрашивается со смещением
- **THEN** запрос заканчивается `OFFSET n ROWS FETCH FIRST m ROWS ONLY`, а не `LIMIT`/`OFFSET`

#### Scenario: Предагрегация в Oracle
- **WHEN** секция по oracle-датасетам считает метрики двух держателей и соединяет агрегаты
- **THEN** подзапросы получают алиасы без `AS`, и запрос принимается источником

#### Scenario: Секция по CSV-датасету
- **WHEN** секция обращается к датасету-CSV
- **THEN** сборка отклоняется с сообщением, что источник пока не поддерживается конструктором

#### Scenario: Разные типы источников в одной секции
- **WHEN** метрики секции лежат в датасетах разных типов источников
- **THEN** сборка отклоняется: кросс-источниковые запросы не поддерживаются

### Requirement: План соединения датасетов
Если секции нужны несколько датасетов, построитель SHALL составлять план соединения: базовым берётся датасет метрик, остальные подключаются по связям словаря. При отсутствии прямой связи SHALL искаться кратчайший путь через промежуточные датасеты — они добавляются в план как мост, своих колонок в отчёт не давая. Если пути нет, сборка SHALL отклоняться с указанием, между чем именно нужна связь.

#### Scenario: Соединение через справочник
- **WHEN** метрики плана и метрики факта связаны каждая со справочником точек, но не друг с другом
- **THEN** справочник добавляется в план как мост, и секция собирается

#### Scenario: Связи нет
- **WHEN** между датасетами секции нет ни одного пути по связям
- **THEN** сборка отклоняется с сообщением, что нужно завести связь в семантическом слое

### Requirement: Защита от размножения строк
Перед соединением построитель SHALL проверять по реальным данным, уникален ли присоединяемый датасет по своему ключу связи, и считать безопасными только те шаги, которые не размножают строки держателя метрик; раздувание транзитивно, поэтому дальше цепочка проходится только через безопасные шаги. Результат проверки уникальности SHALL кэшироваться на время сборки отчёта.

#### Scenario: Разрез, недостижимый безопасно
- **WHEN** пользователь просит метрики плана в разрезе категории, лежащей в таблице продаж, путь к которой размножает строки плана
- **THEN** сборка отклоняется с объяснением, что у показателей этого датасета нет такого разреза

#### Scenario: Две таблицы фактов в одной секции
- **WHEN** секция содержит метрики из двух датасетов, каждый из которых размножает строки другого
- **THEN** запрос собирается предагрегацией: каждый датасет сворачивается до разрезов секции, и соединяются уже агрегаты

### Requirement: Предагрегация и формулы над агрегатами
При предагрегации построитель SHALL считать каждый держатель метрик в своём подзапросе, соединять подзапросы по разрезам секции (FULL OUTER JOIN, при отсутствии разрезов — CROSS JOIN) и склеивать значения разрезов через `coalesce`. Формула, операнды которой лежат в разных датасетах, SHALL вычисляться снаружи, поверх соединённых агрегатов; её операнды добавляются в выдачу подзапросов, даже если пользователь их не выбирал.

#### Scenario: План делённый на факт
- **WHEN** пользователь строит формулу «факт ÷ план», где операнды лежат в разных датасетах
- **THEN** каждый операнд считается в своём подзапросе, деление выполняется поверх соединения, деление на ноль даёт пустое значение, а не ошибку

#### Scenario: Формула в процентах
- **WHEN** формула помечена форматом `percent`
- **THEN** результат приводится к процентам, чтобы фронт показал «12,5 %», а не долю

### Requirement: Фильтры секции
Фильтр SHALL применяться ко всей секции или не применяться вовсе: если разрез фильтра недостижим безопасно хотя бы для одного показателя секции, фильтр SHALL сниматься, а секция — помечаться текстом о том, какие фильтры не применены и почему. Фильтр по разрезу из датасета, не связанного с секцией, SHALL игнорироваться. Датасет снятого фильтра SHALL не оставаться в плане соединения.

#### Scenario: Фильтр применим не ко всем показателям
- **WHEN** секция показывает рядом показатели двух датасетов, а фильтр относится только к одному
- **THEN** фильтр снимается, под секцией выводится пометка с названием фильтра и показателями, у которых такого разреза нет

#### Scenario: Значения select-фильтра
- **WHEN** фронт запрашивает отчёт с select-фильтром
- **THEN** список значений берётся запросом DISTINCT по полю разреза (не более 200 значений); если источник недоступен, фильтр отдаётся без списка

### Requirement: Фильтр-период по дате
Фильтр по разрезу-дате SHALL задаваться периодом: границы приходят отдельными ключами значений — `<разрез>__from` и `<разрез>__to`; пустая граница означает «без ограничения». Обе границы SHALL уходить в SQL параметрами типа «дата». Верхняя граница SHALL сравниваться строго со следующим днём, чтобы метки времени последнего дня периода не выпадали. Значение, не являющееся датой в формате ISO, SHALL игнорироваться, а не ронять отчёт.

#### Scenario: Период за неделю
- **WHEN** читатель задаёт период с 10 по 20 августа
- **THEN** секции считаются только по этому интервалу, включая записи 20 августа с любым временем

#### Scenario: Один день
- **WHEN** обе границы периода равны одной дате
- **THEN** отчёт показывает данные ровно этого дня

#### Scenario: Мусор вместо даты
- **WHEN** в границе периода приходит строка, не являющаяся датой
- **THEN** граница не применяется, остальные фильтры и секции считаются как обычно

### Requirement: Поля и формулы самого отчёта
Построитель SHALL принимать поля, заведённые автором прямо в отчёте: колонка датасета плюс действие из закрытого списка (`sum`, `count`, `count_distinct`, `avg`, `min`, `max`) — как метрика, либо колонка как разрез. Имя колонки SHALL сверяться со схемой датасета, действие — со списком, поэтому произвольный SQL через поле отчёта невозможен. Ключ поля отчёта SHALL не совпадать с именем элемента словаря; формула SHALL ссылаться только на известные показатели.

#### Scenario: Колонки нет в схеме
- **WHEN** определение содержит поле отчёта на колонку, которой нет в схеме датасета
- **THEN** сборка отклоняется с указанием датасета и колонки

#### Scenario: Ключ поля дублирует словарь
- **WHEN** ключ поля отчёта совпадает с slug'ом метрики или разреза словаря
- **THEN** сборка отклоняется с просьбой переименовать поле

### Requirement: Порядок строк при вложенной группировке
Когда секция-таблица сгруппирована больше чем по одному разрезу, построитель SHALL сортировать выдачу сначала по старшим разрезам (по возрастанию), и лишь внутри последнего уровня применять сортировку, выбранную автором отчёта. Без этого строки одной группы не соседствуют, и иерархию в таблице показать нечем.

#### Scenario: Таблица по городу и категории
- **WHEN** таблица сгруппирована по «Городу» и «Категории», а сортировка задана по выручке
- **THEN** города идут по алфавиту, внутри каждого категории отсортированы по выручке

### Requirement: Потолок строк секции
Секция без явного `limit` SHALL отдавать не более 50 000 строк; при обрезке выдачи секция SHALL нести пометку о том, что показана только часть строк, и подсказку взять разрез покрупнее или задать своё ограничение. Собственный `limit` автора отчёта имеет приоритет.

#### Scenario: Разрез высокой кардинальности
- **WHEN** пользователь строит таблицу по разрезу с сотнями тысяч значений и не задал ограничение
- **THEN** возвращаются первые 50 000 строк с пометкой об обрезке, страница остаётся отзывчивой

### Requirement: Сырые строки под секцией
Построитель SHALL уметь отдавать строки без агрегата: тот же план соединения и те же фильтры, что у секции, плюс условия точки. Значение разреза в условии SHALL сравниваться тем же выражением, что стоит в GROUP BY, поэтому гранулярность даты учитывается сама собой. Колонки SHALL браться из схемы датасета-держателя метрик; если держателей несколько, вызывающая сторона выбирает, чьи строки показать.

#### Scenario: Точка по месяцу
- **WHEN** запрошены строки под точкой графика с гранулярностью «по месяцам»
- **THEN** в выборку попадают все дни этого месяца, а не только первое число

#### Scenario: Схема датасета не вычитана
- **WHEN** у датасета нет вычитанной схемы
- **THEN** запрос строк отклоняется с просьбой обновить схему в «Датасетах»

### Requirement: Понятные ошибки источника
Ошибку источника построитель SHALL переводить в фразу для того, кто SQL не писал: недоступность источника — как временную, пропавшую колонку — с именем колонки и советом пересоздать поле отчёта, внутренний дефект сборки запроса — как ошибку конструктора с советом убрать последнее добавленное поле и сообщить о проблеме. Технические подробности и сам SQL SHALL оставаться в логе сервера.

Пропавшая колонка SHALL распознаваться по сообщениям всех поддерживаемых источников (PostgreSQL `column "x" does not exist`, ClickHouse `Unknown identifier`, Oracle `ORA-00904: "T0"."X": invalid identifier`) — имя колонки SHALL доходить до человека без кавычек и квалификатора. Недоступность источника SHALL распознаваться в том числе по кодам драйвера Oracle (`DPY-*`) и сети Oracle (`TNS:`, `ORA-125xx`, `ORA-12170`).

#### Scenario: Колонка удалена из источника Oracle
- **WHEN** отчёт ссылается на поле, которого больше нет в таблице Oracle
- **THEN** пользователь видит «в источнике больше нет колонки «REVENUE» …», а не текст ORA-00904

#### Scenario: Колонка исчезла из источника
- **WHEN** запрос падает с ошибкой «column ... does not exist»
- **THEN** пользователь видит, что в источнике больше нет этой колонки и поле отчёта нужно пересоздать или убрать

#### Scenario: Источник не отвечает
- **WHEN** запрос падает по таймауту или обрыву соединения
- **THEN** пользователь видит предложение повторить через минуту, без технических деталей

### Requirement: Один снимок словаря на сборку
Сборка отчёта SHALL читать словарь (метрики, разрезы, связи, датасеты) один раз и переиспользовать соединения с источниками до конца сборки, закрывая их в конце. Это относится и к проверкам уникальности по ключам связей.

#### Scenario: Отчёт из нескольких секций
- **WHEN** отчёт содержит несколько секций по одному источнику
- **THEN** словарь читается один раз, соединение с источником открывается один раз и закрывается после сборки всех секций
