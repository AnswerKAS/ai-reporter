# Proposal: builder-server-filter

## Why

Датасетов бывает тысяча, и лежат они не на одном сервере: десять серверов
PostgreSQL, десять Oracle, десять ClickHouse, на каждом по десятку витрин
(об этом же — изменение `dataset-connections`). Отбор на шаге «Данные»
(`builder-dataset-picker`) умеет фильтровать по **типу** СУБД, но тип на
тридцати серверах не сужает почти ничего: «PostgreSQL» — это триста
датасетов с десяти разных машин.

Это не косметика. Секция отчёта собирается **в пределах одного сервера**:
связь датасетов заводится только между датасетами с одинаковым резолвленным
DSN (`semantic/registry.py:validate_link`), а построитель джойнит датасеты
одного типа источника. Датасет с другого сервера в секцию не встанет — и
автору надо видеть это до того, как он его выберет, а не после того, как
предпросмотр не собрался.

Сегодня узнать сервер датасета из интерфейса нельзя вовсе: `dsn` не выходит
за пределы бэкенда (креды), а никакого другого признака сервера у датасета
нет.

## What Changes

- **У датасета появляется тождество сервера** — `serverId` и `serverTitle` в
  `GET /api/datasets`. Считает их новый `datasets/servers.py`: DSN сводится к
  четвёрке (тип СУБД, хост, порт, база) — `postgresql://` и `postgres://`,
  умолчания портов и разный порядок параметров дают **один** сервер, а разные
  логины на одной базе перестают быть разными серверами.
- **Адрес наружу не уходит.** Обычный пользователь видит имя вида
  «PostgreSQL · сервер 2» — номер, устойчивый в пределах установки (порядок
  задаёт самый ранний датасет сервера). Хост, порт и база подставляются в имя
  **только администратору**: конвенция «секреты (DSN, логины, пароли, хосты)
  не выводятся в API и UI» остаётся в силе, а отбирать датасеты по серверу
  номера достаточно.
- **Фильтр по серверу на шаге «Данные»**: выпадающий список рядом с поиском и
  фильтрами (`Select`, а не `Chips` — серверов бывает тридцать, полосой чипов
  они не помещаются), варианты сгруппированы по типу СУБД и несут счётчик
  датасетов, наверху — «Все серверы». Выбранный сервер складывается с
  остальными фильтрами.
- **Карточка датасета называет сервер** — там же, где источник и таблица:
  выбор «этот или тот» без ухода со страницы.
- **CSV-датасеты сервера не имеют**: источник — файл в хранилище артефактов.
  Они собираются в отдельный вариант «Без сервера (CSV)», а не притворяются
  сервером.

## Capabilities

### Modified Capabilities

- `datasets` — тождество сервера у датасета и его выдача в API
  (specs/datasets/spec.md)
- `report-builder` — отбор датасетов по серверу на шаге «Данные»
  (specs/report-builder/spec.md)

## Impact

- **Бэкенд**: новый `app/datasets/servers.py` (нормализация DSN до тождества
  сервера, нумерация, имена), `api/datasets.py` (`_meta` получает индекс
  серверов; индекс считается один раз на запрос, а не на датасет),
  `schemas/dataset.py` (`server_id`, `server_title` в `DatasetMeta`).
- **Фронт**: `types/dataset.ts` (`serverId`, `serverTitle`),
  `components/builder/DatasetPicker.tsx` (список серверов, фильтр, сервер на
  карточке).
- **Тесты**: новый `tests/test_dataset_servers.py` (нормализация: схемы-синонимы,
  умолчания портов, разные логины, `env:VAR`, `app:postgres`, битый DSN, CSV),
  дополнение `tests/test_api_datasets.py` (поля в выдаче, адрес — только
  админу). Новых методов API нет, опись `test_routes.py` не меняется.
- **Что остаётся за границей изменения**: сущности «подключение» это не
  создаёт — `serverId` считается из DSN. Когда `dataset-connections` заведёт
  подключения, `serverId` станет `connection_id`, а `serverTitle` — названием
  подключения, которое даст администратор; форма отбора в конструкторе при
  этом не меняется. Фильтр добавляется только на шаг «Данные» конструктора;
  страница `/datasets` со своими фильтрами — отдельный разговор.
