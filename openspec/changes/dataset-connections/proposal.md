# Proposal: dataset-connections

## Why

Сервер источника сейчас живёт внутри датасета: колонка `datasets.dsn` — литеральная
строка подключения, которую администратор набирает руками в админке (изменение
`dataset-admin-create` убрало форматы-указатели `env:VAR` и `app:postgres` и
перенесло заведение датасета в `/admin?tab=datasets`). Пока серверов два-три,
это терпимо. На тридцати (десять
PostgreSQL, десять Oracle, десять ClickHouse, а на каждом по десятку витрин)
схема разваливается сразу по пяти швам:

1. **Пароль лежит в метабазе и набирается руками.** DSN с кредами вводится в
   форму датасета и хранится текстом. На каждый датасет — своя копия: один
   сервер и десять витрин означают десять паролей в базе и десять правок при
   ротации, из которых девять исправленных — это молча сломанный отчёт.
2. **Строка вместо полей.** Хост, порт, база, схема TLS, percent-encoding
   пароля — всё это администратор собирает в голове и записывает одной
   строкой. Опечатка в ней ловится только проверкой подключения, а сообщение
   об ошибке приходится маскировать, чтобы не вынести креды наружу.
3. **Серверов не видно.** Ни списка, ни статуса, ни «кто на нём сидит».
   Вопрос «что у нас лежит на `pg-prod-2` и что сломается, если его погасить»
   сегодня отвечается только чтением метабазы.
4. **Сервер нельзя проверить отдельно от датасета.** Проверка подключения
   есть только у датасета вместе с вычиткой схемы.
5. **Тождество базы определяется сравнением строк.** `validate_link` сверяет
   резолвленные DSN двух датасетов дословно (`semantic/registry.py`).
   `postgresql://u:p@db/x` и `postgres://u:p@db/x?sslmode=require` — одна база,
   но связь между их датасетами отклоняется; наоборот, две записи одной базы с
   разными логинами считаются разными. Построитель же (`query/builder.py`)
   проверяет вообще только **тип** источника: два датасета в разных базах
   PostgreSQL для него «один источник», и от неверного джойна спасает только
   то, что связь между ними завести не дали.

## What Changes

- **Новая сущность «подключение»** (`connections` в метабазе) — это одна база
  на одном сервере, описанная **полями, а не строкой**: тип СУБД
  (`postgres` | `oracle` | `clickhouse`), хост, порт (умолчание по типу), имя
  базы (для Oracle — сервис или SID), имя переменной окружения с **логином**,
  имя переменной окружения с **паролем**, при необходимости — TLS/`sslmode`.
- **Креды берутся только из окружения.** В метабазе хранятся **имена**
  переменных, а не значения: пароль не попадает ни в базу, ни в API, ни в
  журнал. Ротация — это правка `.env` и перезапуск, а не тридцать правок в
  интерфейсе.
- **Литеральных DSN в интерфейсе и API не остаётся.** Строка подключения
  собирается в памяти в момент соединения (`build_dsn`) — единственное место,
  где она вообще существует.
- **Датасет ссылается на подключение** (`datasets.connection_id`), а не носит
  DSN. У CSV-датасета подключения нет — источник лежит в хранилище артефактов.
- **Разовая миграция при старте**: каждое различающееся значение
  `datasets.dsn` (в том числе оставшиеся с прежних времён `env:VAR` и
  `app:postgres` — их резолвер и уходит вместе с миграцией) разбирается на
  хост, порт и базу и становится подключением;
  сами креды из старой строки перенести в окружение автоматически нельзя,
  поэтому мигрированное подключение продолжает работать по сохранённой строке
  и **помечается как требующее перевода на переменные окружения**, пока
  администратор не укажет их имена. Ручных шагов при обновлении нет, отчёты не
  ломаются.
- **Новые методы API** (`/api/admin/connections`, только админ): список со
  счётчиком датасетов, создание, правка, **проверка подключения** отдельно от
  датасета, удаление (409, пока на подключении есть датасеты).
- **Связи датасетов — только внутри одной базы.** Тождество базы становится
  ссылкой на подключение, а не совпадением строк: `validate_link` и
  построитель секции сверяют `connection_id`. Построитель начинает отклонять
  секцию, датасеты которой лежат в разных базах одного типа СУБД, — сегодня он
  такую секцию собирает и адресует базе первого датасета.
- **Смена подключения у датасета** (`PATCH /api/datasets/{slug}`) — переезд
  витрины в другую базу перестаёт быть пересозданием датасета с потерей
  метрик и разрезов.
- **Интерфейс**: вкладка «Подключения» в админке (по образцу почтовых
  серверов) — список, форма полями, «Проверить», удаление; в форме датасета
  вместо поля DSN — выбор подключения нужного типа с возможностью завести
  новое, не уходя со страницы; на карточке датасета видно, в какой базе он
  лежит; в фильтрах страницы датасетов появляется отбор по подключению.

## Capabilities

### New Capabilities

- (нет — расширяются существующие)

### Modified Capabilities

- `datasets` — подключение полями и кредами из окружения, датасет ссылается на
  него (specs/datasets/spec.md)
- `semantic-model` — связи только внутри одной базы, тождество по
  `connection_id` (specs/semantic-model/spec.md)
- `query-engine` — секция собирается в пределах одной базы
  (specs/query-engine/spec.md)
- `platform` — таблица подключений, переменные окружения с кредами и разовая
  миграция DSN (specs/platform/spec.md)

## Impact

- **БД**: новая таблица `connections` (поля адреса + имена переменных
  окружения), колонка `datasets.connection_id`
  (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`), разовая миграция
  `datasets.dsn` → подключения. Колонка `datasets.dsn` остаётся в таблице (её
  читает только миграция), но перестаёт быть источником правды.
- **Бэкенд**: новый `app/datasets/connections.py` (реестр, чтение кредов из
  окружения, сборка DSN, проверка), `app/api/connections.py` (5 методов),
  правки `datasets/registry.py` (фабрика адаптеров берёт параметры у
  подключения; `resolve_dataset_dsn` и резолвер старых форматов-указателей
  уходят целиком), `api/datasets.py` (создание и правка по `connectionId`;
  `_validate_dsn` и `DSN_SCHEMES` уходят), `schemas/dataset.py`, `semantic/registry.py`
  (`validate_link`), `query/builder.py` (одна база на секцию),
  `core/database.py` (схема и миграция).
- **Фронт**: `types/dataset.ts`, `lib/api.ts`, новая
  `components/admin/ConnectionsPanel.tsx` и вкладка в `AdminPage`; форма
  заведения (`components/admin/DatasetsPanel.tsx`) меняет поле DSN на выбор
  подключения; `pages/DatasetsPage.tsx` — подключение на карточке и фильтр по
  нему.
- **Тесты**: новый `tests/test_api_connections.py`, опись методов в
  `tests/test_routes.py`, правки `conftest.py` (датасеты фикстур заводятся на
  подключении) и тестов датасетов, словаря и построителя.
- **Эксплуатация**: у каждого сервера появляется пара переменных в `.env`
  (`deploy/` и README нужно дополнить) — это единственное место, где живут
  креды источников.
- **Совместимость**: `dsn` уходит из тела `POST/PATCH /api/datasets` —
  единственный клиент API это наш фронт, он меняется в том же изменении.
- **Права не двигаются**: подключения заводит и видит только администратор,
  остальным видно лишь название подключения в карточке датасета.
