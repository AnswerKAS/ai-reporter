# Design: reports-navigator

## Почему группировка ленивая, а не разворачиванием строк

Разрезы «группа доступа» и «тема» многозначны: отчёт лежит в трёх группах и
несёт два тега. Отдавать группировку одной выдачей — значит размножать строки
(отчёт приезжает трижды с разным `groupKey`), а `total` и `offset` перестают
означать «отчётов» и начинают означать «пар отчёт-группа»: пагинация по такой
выдаче не читается ни человеком, ни кодом.

Поэтому группировка собрана из двух уже существующих кусков:

- **заголовки групп со счётчиками** — из `GET /api/reports/facets`, один
  агрегатный запрос на все разрезы;
- **строки внутри группы** — обычным `GET /api/reports?group=<id>` при
  раскрытии.

Раскрытая группа — это тот же постраничный список, что и корневой. Ни одного
нового понятия в API, и группа на три тысячи отчётов не разворачивается в DOM
целиком.

## Значение `-`: «ни одной»

У фильтров `group`, `author` и `tag` есть особое значение `-` — «без группы»,
«без автора», «без темы». Без него разрез врёт: сумма счётчиков по вариантам
меньше `total`, и человек не понимает, куда делись остальные отчёты. Именно в
это ведро попадают все отчёты, заведённые до появления `created_by`.

## Почему темы — отдельная таблица, а не колонка

`report_tags(report_slug, tag)` вместо `reports.tags TEXT` с JSON: по колонке
не собрать ни фасетных счётчиков, ни фильтра — только `LIKE` по тексту, который
поймает `продажи` внутри `продажи-юг`. Таблица даёт `GROUP BY tag` и точное
сравнение, и одинаково работает в PostgreSQL и в SQLite, на которой стоит
набор тестов.

## Доступ считается в SQL

`accessible_slugs()` читает все назначения пользователя и отдаёт множество, по
которому список фильтровался в Python. При постраничной выдаче это неверно:
чтобы отдать вторую сотню, пришлось бы прочитать все отчёты. Каталог
подставляет тот же вопрос подзапросом в `WHERE`, а `accessible_slugs()`
остаётся для точечных проверок доступа к одному отчёту.

## Совместимость `/api/reports`

Без параметров метод отдаёт весь список, как раньше. Это не задел на будущее, а
условие безопасной пересадки: конструктор, страница отчёта и рассылки читают
список целиком, и менять их в одном заходе с меню — значит проверять всё сразу.
Меню зовёт метод с `limit`, и только оно.

## Виртуализации нет

Строки не рисуются окном по скроллу — их просто не бывает много: страница
`limit=100`, следующая догружается по достижении конца списка. Виртуализация
понадобилась бы, если бы данные были уже на клиенте; здесь их там нет.
