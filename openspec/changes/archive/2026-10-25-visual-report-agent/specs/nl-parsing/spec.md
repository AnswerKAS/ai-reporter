## MODIFIED Requirements

### Requirement: Диалоговый разбор описания
Система SHALL принимать реплику об отчёте, текущую раскладку, поля и выбранные датасеты и возвращать ответ по-русски вместе с полным определением отчёта. Переписка SHALL храниться в метабазе по пользователю и цели отчёта; клиент SHALL восстанавливать её. Контекст модели SHALL ограничиваться последними репликами. Ответ SHALL называть модель, когда она использовалась. Без ключа модели SHALL использоваться детерминированный парсер с `source: parser`; если однозначный показатель не назван, сервер SHALL выбрать один пригодный вариант, а не показывать список вариантов сотруднику. `POST /api/reports/recommendations` MAY сохраняться для совместимости старых клиентов.

#### Scenario: Правка собранного
- **WHEN** сотрудник просит добавить фильтр к предложенной раскладке
- **THEN** возвращается полное определение с добавленным фильтром

#### Scenario: Переписка помнится сервером
- **WHEN** сотрудник возвращается после перезагрузки страницы
- **THEN** сохранённые реплики используются при следующем ходе

#### Scenario: Нет ключа модели
- **WHEN** сотрудник отправляет описание без ключа модели
- **THEN** диалог возвращает конкретную раскладку с `source: parser`

#### Scenario: Неясная реплика без модели
- **WHEN** парсер не может однозначно выбрать показатель
- **THEN** сервер выбирает один пригодный отчёт по словарю

#### Scenario: Уточнение вместо отчёта
- **WHEN** у агента недостаточно данных для проверенного отчёта
- **THEN** он объясняет, какие данные или формулировка нужны для продолжения

#### Scenario: Совместимость с клиентской историей
- **WHEN** старый клиент присылает всю переписку
- **THEN** сервер использует сохранённую историю, а новую реплику добавляет к ней

#### Scenario: Нужное поле вне выбранного датасета
- **WHEN** поле отсутствует в выбранном датасете, но есть в общем словаре
- **THEN** агент может включить его из другого датасета

#### Scenario: Сотрудник просит отчёт без названия полей
- **WHEN** сотрудник просит собрать отчёт без названия показателей
- **THEN** агент или парсер выбирает конкретную раскладку по доступным данным

#### Scenario: Варианты до разговора
- **WHEN** сотрудник открывает новый чат конструктора
- **THEN** интерфейс показывает поле описания без готовых вариантов

#### Scenario: Ошибочный показатель
- **WHEN** поле или датасет имеет статус ошибки
- **THEN** агент не предлагает блок по неисправному источнику

## ADDED Requirements

### Requirement: Потоковый диалог конструктора
Конструктор SHALL передавать события работы агента и ответ по мере выполнения через `POST /api/reports/chat/stream`. Завершённый ход SHALL сохраняться в серверном диалоге с привязкой к пользователю и цели отчёта; последующие реплики SHALL использовать сохранённый контекст.

#### Scenario: Построение отчёта
- **WHEN** агент изучает данные и проверяет секции
- **THEN** пользователь видит прогресс, затем ответ и применённую раскладку

#### Scenario: Работа без модели
- **WHEN** модель не настроена и запрос не называет однозначный показатель
- **THEN** парсер выбирает один подходящий готовый отчёт и возвращает его определение без списка вариантов для пользователя
