# Proposal: reports-navigator

## Why

Левое меню — плоский список всех доступных отчётов: `GET /api/reports` отдаёт
их одним массивом, контекст держит массив в памяти, `ReportTree` фильтрует его
`Array.filter`. Пока отчётов три десятка, это ровно то, что нужно.

На десяти тысячах отчётов ломается всё сразу:

- **ответ весит мегабайты** и едет при каждой загрузке страницы, потому что
  список нужен меню на всех экранах;
- **в DOM встаёт десять тысяч строк** — меню начинает подтормаживать на
  прокрутке и на каждом нажатии клавиши в поиске;
- **найти отчёт нечем, кроме подстроки в названии**: разрезов у отчёта нет
  вовсе. В схеме `reports` нет ни автора, ни тем, а группа доступа лежит в
  `report_access`, куда список не смотрит.

При этом человек на таком объёме ходит в пять-десять отчётов из десяти тысяч, и
ни один список этого не знает: закрепить отчёт негде, «где я был вчера» —
тоже.

## What Changes

- **Каталог отчётов переезжает на сервер.** `GET /api/reports` принимает поиск,
  фильтры и страницу (`q`, `group`, `author`, `tag`, `status`, `favorite`,
  `sort`, `limit`, `offset`) и отдаёт страницу вместе с `total`. Доступ
  фильтруется в SQL, а не выборкой в Python после чтения всей таблицы. Без
  параметров метод отвечает как раньше — целым списком: на нём держатся
  страницы, которым каталог не нужен.
- **Фасеты одним запросом.** `GET /api/reports/facets` отдаёт разрезы со
  счётчиками: группы доступа, авторы, темы, статусы, число избранных и общее
  число. Счётчик у варианта равен тому, что даст его нажатие.
- **Избранное.** `PUT`/`DELETE /api/reports/{slug}/favorite` — своё у каждого
  пользователя (`report_favorites`). Закреплённые всегда наверху меню.
- **Автор отчёта.** `reports.created_by` пишется при создании; у отчётов,
  заведённых раньше, автор пустой — вывести его неоткуда, и разрез честно
  показывает их как «без автора».
- **Темы.** `report_tags` — свободные метки, правятся там же, где название и
  описание (`PATCH /api/reports/{slug}`, поле `tags`). Тема ничем не выводится
  из данных: её ставит человек.
- **Меню становится навигатором:** закреплённые и недавние сверху, поиск с
  задержкой уходит на сервер, полоса фильтров (`Chips` со счётчиками),
  переключатель «Группировать по» (без группировки / по группе доступа / по
  автору / по теме), догрузка страницами по мере прокрутки. Кнопки на строке —
  конструктор, переименование, удаление — остаются и дополняются контекстным
  меню: на тач-устройствах наведения нет, а сейчас кнопки видны только по нему.
- **Группировка ленивая:** заголовки групп со счётчиками приходят из фасетов,
  строки группы догружаются при раскрытии. Раскрытая группа на три тысячи
  отчётов не разворачивается в DOM целиком.

## Capabilities

### New Capabilities

- (нет — расширяются существующие)

### Modified Capabilities

- `reports` — каталог отчётов: страница, поиск, фильтры, фасеты, избранное,
  автор и темы (specs/reports/spec.md)
- `web-ui` — левое меню как навигатор по каталогу (specs/web-ui/spec.md)

## Impact

- **Миграции метабазы:** `reports.created_by`, таблицы `report_favorites` и
  `report_tags`. Обратной засыпки автора нет — она невозможна.
- **Контракт `/api/reports`** расширяется без слома: старый вызов без
  параметров отвечает как прежде.
- **Фронт:** `lib/reports.tsx` перестаёт держать весь список — контекст теперь
  хранит фасеты, избранное и недавние, а страницы отчётов запрашивают выдачу
  постранично (`useReportSearch`). Затрагиваются `ReportTree`, `Sidebar`,
  `ReportListPage`, `AccountPage`, `account/ReportsPanel`.
- **Права не двигаются:** каталог сужает то, что API и так отдал бы
  вызывающему; удаление по-прежнему только администратору.
