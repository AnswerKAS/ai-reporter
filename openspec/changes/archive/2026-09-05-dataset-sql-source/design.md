# Design: dataset-sql-source

## Context

См. proposal.md — Why. Ключевые факты о текущем коде, на которых стоят решения:

- `quoted_table()` вне адаптеров зовётся ровно в пяти местах: `query/builder.py`
  (`_is_unique_on`, `_from_sql`, `distinct_values`), `reports/drilldown.py` (`dataset_rows`),
  `semantic/registry.py` (`validate_metric`). Алиас таблице вешает **только** `_from_sql`.
- `PostgresAdapter.run_query` вызывает `cur.execute(sql, params or {})`. Пустой словарь —
  это не `None`, и psycopg включает разбор шаблона в любом случае.
- `clickhouse_connect.driver.binding` при пустых параметрах текст запроса не трогает,
  при непустых — ищет `{имя:Тип}` по всему тексту и отдаёт подстановку серверу.
- Slug'и метрик и разрезов лежат в разных таблицах, но `reports/drilldown.py` резолвит их
  как `catalog.metrics.get(s) or catalog.dimensions.get(s)` — пространство имён общее.

## Goals / Non-Goals

**Goals:**
- Датасет на произвольном SELECT без записи в источник.
- Схема и превью такого датасета — как у обычного.
- Путь «вставил SQL → работающий отчёт» без ручного заведения словаря по одной форме.

**Non-Goals:**
- Не делаем SQL доступным обычному пользователю: это по-прежнему инструмент администратора.
- Не материализуем результат (ни таблицей, ни кэшем): «данные всегда живые» — свойство системы.
- Не поддерживаем SQL-датасеты для CSV: у него нет движка запросов (`csvsource.run_query` бросает).

## Decisions

- **Подзапрос, а не `CREATE VIEW` в источнике.** Вьюха требует прав на запись в чужую базу
  и оставляет там объекты, за жизненный цикл которых система не отвечает (переименовали
  датасет — вьюха осталась; удалили датасет — вьюха осталась). Подзапрос ничего не оставляет.
  Цена — запрос исполняется заново на каждую секцию отчёта, на каждый список значений фильтра
  и на детализацию; это ровно та же цена, что у обычного датасета на вьюхе, и она честно
  показана в интерфейсе.
- **`table_name` и `query` взаимоисключающие**, а `source` не расширяется значением вроде
  `postgres-sql`. `source` выбирает адаптер и диалект — это тип СУБД, а не способ адресации.
- **Алиас подзапроса даёт вызывающий** (`source_sql(alias)`), а не адаптер: подзапрос в `FROM`
  без алиаса в PostgreSQL до 16-й версии — синтаксическая ошибка, а четыре из пяти
  call-site'ов сегодня пишут голое `FROM {table}`.
- **`%` удваивается внутри `PostgresAdapter.source_sql()`** — там, где известно, что результат
  идёт в `run_query` вместе со словарём параметров. Собственные запросы адаптера
  (`fetch_schema`, `sample_rows`) исполняются без параметров и берут сырой текст.
  Инвариант хрупкий, поэтому он записан комментариями в обоих местах.
- **`{имя:Тип}` в ClickHouse запрещаем, а не экранируем** — экранирования на стороне сервера
  не существует, и подстановка ломает запрос даже при пустых параметрах клиента.
- **Валидация SQL — страховка, а не граница безопасности.** Границей остаётся `require_admin`.
  Список запретных слов ловит опечатку и «вставил два запроса», но не злоумышленника
  с правами администратора; настоящая защита источника — read-only пользователь в DSN.
  Это записано в докстринге модуля, чтобы список не начали «усиливать» как защиту.
- **Черновик словаря подтверждается галочками, а не заводится молча.** Словарь — общий
  для всех отчётов, slug'и в нём глобальны, и «выручка» обязана означать одно и то же.
  Автозавод пятнадцати метрик по угадыванию типов засорил бы его необратимо.
- **Два эндпоинта, а не один с `dry_run`.** `GET /suggest` — чистая функция от уже вычитанной
  схемы, без побочных эффектов и без обращения к источнику; `POST /semantic` заводит выбранное.
  Один URL с двумя контрактами ответа читался бы хуже.
- **Отдельного «проверить, ничего не создавая» нет.** `POST /api/datasets` уже завершается
  вычиткой схемы и возвращает статус, ошибку и поля, а цикл правки закрывают `PATCH` и
  существующая кнопка «Проверить и вычитать схему» — новый контракт не нужен.
- **Соединение адаптера PostgreSQL переводится в autocommit.** Вскрылось на пакетной
  проверке метрик: без него первое же упавшее выражение переводит транзакцию в aborted,
  и на переиспользуемом соединении начинает падать всё последующее — валидные метрики
  помечались бы ошибкой, а соседние секции отчёта не собирались бы после первой неудачной.
  Датасет только читает, транзакция ему не нужна.
- **Текст запроса отдаётся только администратору.** Кредов в нём нет (DSN — отдельная колонка),
  но `GET /api/datasets` открыт любому авторизованному, а в `WHERE` бывают зашиты имена схем
  и служебные значения. Остальным видно только, что источник — запрос.

## Risks / Trade-offs

- [Тяжёлый запрос исполняется на каждую секцию и на проверку уникальности ключа связи —
  отчёт становится медленным] → предупреждение в интерфейсе + совет выносить тяжёлую
  агрегацию во вьюху или матвью источника и заводить датасет на ней.
- [`%` в PostgreSQL: при удвоении не в том месте запрос отработает, но вернёт 0 строк —
  тихая неправда вместо ошибки] → отдельный сценарий приёмки на `LIKE` с фильтром и без.
- [`DESCRIBE (<sql>)` в ClickHouse] → проверен на живом сервере: типы приходят как есть
  (`LowCardinality(String)`, `Date`, `Float64`), запасной путь `SELECT * FROM (<sql>) LIMIT 0`
  не понадобился.
- [Правка SQL у живого датасета может убрать колонку, на которую ссылается разрез отчёта] →
  после сохранения сразу вычитывается схема, а в ответе возвращается список разрезов и
  метрик, чьих полей больше нет. Метрики и так получают статус `error`, разрезы — нет.
- [Автоматически выведенные метрики могут быть бессмысленны (`sum` по идентификатору)] →
  такие предложения по умолчанию не отмечены, а названия и slug'и редактируются до заведения.

## Migration Plan

`ALTER TABLE datasets ADD COLUMN IF NOT EXISTS query TEXT` при старте — у существующих
датасетов NULL, поведение не меняется. Замена `quoted_table` на `source_sql` в пяти
call-site'ах для табличных датасетов даёт тот же SQL (алиас в четырёх местах новый, но
безымянных ссылок на колонки он не ломает). Откат — снятие change; колонка остаётся пустой
и никем не читается.
