# reports — сборка и рендеринг отчётов

## Purpose

Возможность описывает жизненный цикл отчёта: создание по скиллу, фоновую сборку через LLM-агент или демо-скрипт, валидацию спеки, фильтры с realtime-пересчётом и рендеринг секций (KPI, графики с детализацией по клику, комбо-графики, таблицы).

## ADDED Requirements

### Requirement: Создание отчёта по скиллу
Администратор SHALL иметь возможность создать отчёт, указав скилл (`домен/имя`), slug, название, параметры и режим сборки (`auto` | `demo` | `llm`). Slug по умолчанию — `домен-имя-<hex>`; дубликаты slug отклоняются с ошибкой 409.

#### Scenario: Создание с валидным скиллом
- **WHEN** администратор отправляет `POST /api/reports` с существующим скиллом и режимом demo
- **THEN** API возвращает 202, отчёт попадает в очередь со статусом `queued`, фоновый воркер берёт его в сборку (`building`) и по завершении переводит в `ready`

#### Scenario: Несуществующий или служебный скилл
- **WHEN** администратор указывает скилл, которого нет в `backend/skills/`, или имя с префиксом `_`
- **THEN** API отклоняет создание с ошибкой 404/400 и отчёт не создаётся

### Requirement: Сборка отчёта
Система SHALL собирать отчёт фоновым воркером: в режиме `llm` — через агента opencode, который генерирует скрипт `report.py` по тексту скилла; в режиме `auto` — с автоматическим fallback на демо-скрипт при недоступности агента; в режиме `demo` — только демо-скрипт. Скрипт SHALL выполняться с переменными окружения `SKILL`, `PERIOD`, `DATABASE_URL`, `FILTER_<KEY>` и `DATASET_<SLUG>_DSN`, и записывать JSON-спеку ReportSpec, которая валидируется перед сохранением.

#### Scenario: LLM-агент недоступен в режиме auto
- **WHEN** opencode не отвечает или завершился с ошибкой, а режим отчёта — `auto`
- **THEN** воркер собирает отчёт демо-скриптом, отчёт переходит в `ready`

#### Scenario: Ошибка сборки в режиме llm
- **WHEN** агент не смог сгенерировать валидный скрипт, а режим — `llm`
- **THEN** отчёт переходит в `error` с текстом ошибки, ранее сгенерированный `report.py` сохраняется

### Requirement: Пересчёт данных при чтении
Система SHALL пересчитывать данные отчёта (запуск `report.py`) при каждом `GET /api/reports/{slug}`; если пересчёт не удался — отдавать последнюю сохранённую спеку (last-known-good), чтобы отчёт оставался доступным.

#### Scenario: Источник данных недоступен
- **WHEN** `report.py` не смог подключиться к БД при чтении отчёта
- **THEN** API возвращает отчёт со статусом `ready` на основе последней валидной спеки

### Requirement: Фильтры с немедленным пересчётом
Спека отчёта MAY объявлять фильтры (`select`/`number`/`text` со списком options); пользователь SHALL иметь возможность сохранить значения фильтров через `POST /api/reports/{slug}/filters`, после чего отчёт пересчитывается немедленно. Значения select применяются только если входят в options (защита от SQL-инъекций); пустая строка означает выключенный фильтр.

#### Scenario: Применение фильтра по региону
- **WHEN** пользователь сохраняет значение `region = Москва` и это значение есть в options
- **THEN** скрипт отчёта получает `FILTER_REGION=Москва`, возвращает только данные по Москве, и фронт показывает отфильтрованные секции

### Requirement: Секции отчёта
ReportSpec SHALL поддерживать секции типов `markdown`, `kpi` (карточки с форматами money/number/percent и дельтами), `chart` (kind: `bar`/`line`/`area`/`pie`/`combo`, у серий combo — `type: bar|line`) и `table`. Секция chart MAY содержать блок `detail` (title с `{point}`, columns, rowsBy), и тогда фронт SHALL открывать по клику на точку графика модальное окно с таблицей детализации, где ключ — значение xKey точки.

#### Scenario: Детализация по клику
- **WHEN** пользователь кликает на столбец bar-графика, у секции которого есть `detail`, и значение точки совпадает с ключом `rowsBy`
- **THEN** открывается модальное окно с таблицей строк детализации и заголовком, где `{point}` заменён на имя точки

#### Scenario: Комбо-график
- **WHEN** спека содержит chart с kind `combo` и сериями разных типов
- **THEN** столбцы рендерятся на левой оси Y, линии — на правой

### Requirement: Перекомпиляция отчёта
Администратор SHALL иметь возможность перекомпилировать `report.py` по актуальному тексту скилла (`POST /api/reports/{slug}/recompile`); прошлая рабочая версия скрипта сохраняется до успешной сборки, и при сбое отчёт продолжает работать на ней.

#### Scenario: Успешная перекомпиляция
- **WHEN** администратор запускает перекомпиляцию и агент сгенерировал валидный скрипт
- **THEN** новый `report.py` заменяет старый, отчёт пересчитывается с новыми данными
