# skill-drafts — генерация и модерация скиллов

## Purpose

Возможность описывает черновики скиллов: генерацию агентом по словесному описанию и выбранным датасетам, отказ при недостатке данных, проверку правилами агентом-ревьюером и публикацию с созданием отчёта.

## ADDED Requirements

### Requirement: Генерация черновика по описанию
Любой авторизованный пользователь SHALL иметь возможность создать черновик (`POST /api/skill-drafts`): домен, имя, название, словесное описание желаемого отчёта и выбранные датасеты. Черновик создаётся со статусом `generating`, агент в фоне пишет markdown-скилл по правилам `report-skill` и метаданным схем выбранных датасетов; результат — статус `draft` с текстом скилла.

#### Scenario: Успешная генерация
- **WHEN** пользователь создал черновик с корректным описанием и датасетом со вычитанной схемой
- **THEN** после работы агента черновик переходит в `draft`, текст скилла доступен для просмотра

### Requirement: Отказ при недостатке данных
Агент SHALL сверять запрос пользователя с реальными полями выбранных датасетов и не выдумывать поля. Если данных недостаточно, агент возвращает структурированный отказ (`reason` + `suggestions`), и черновик переходит в статус `unavailable`; причина и предложения видны пользователю, который может изменить запрос и перегенерировать. Если у всех выбранных датасетов схемы не вычитаны — отказ выдаётся сразу, без вызова агента.

#### Scenario: Запрошенных данных нет
- **WHEN** пользователь описал разрез, которого нет в полях датасетов (например «продажи по цветам глаз»)
- **THEN** черновик переходит в `unavailable` с причиной и списком возможных альтернатив на имеющихся полях

#### Scenario: Перегенерация с новым запросом
- **WHEN** пользователь в карточке черновика изменил текст запроса и запустил перегенерацию
- **THEN** описание черновика обновляется, статус возвращается в `generating`

### Requirement: Отправка на модерацию
Автор черновика SHALL иметь возможность отправить черновик со статусом `draft` (или `rejected`) на публикацию (`POST /{id}/submit`) — статус `review`. Свои черновики автор видит всегда; админ видит все.

#### Scenario: Черновик в статусе generating
- **WHEN** автор пытается отправить на модерацию черновик, который ещё генерируется
- **THEN** API возвращает 409 и статус не меняется

### Requirement: Проверка по правилам
Администратор SHALL иметь возможность запустить проверку черновика агентом-ревьюером (`POST /{id}/check`): ревьюер сверяет скилл с правилами каркаса и возвращает вердикт `ok` с пустым списком замечаний либо `issues`. Статус становится `checked` (при ok) или `rejected` (с замечаниями).

#### Scenario: Ревьюер нашёл замечания
- **WHEN** агент-ревьюер вернул вердикт с непустым списком замечаний
- **THEN** статус черновика — `rejected`, замечания видны в карточке

### Requirement: Публикация скилла
Администратор SHALL иметь возможность опубликовать черновик в статусе `checked`: текст скилла записывается в `backend/skills/<домен>/<имя>.md`, автоматически создаётся отчёт (mode `auto`, slug `домен-имя-<hex>`), автору выдаётся доступ к отчёту через `report_access`; статус черновика — `published`. Опубликованный черновик нельзя перегенерировать или удалить через черновик.

#### Scenario: Публикация после проверки
- **WHEN** администратор публикует черновик со статусом `checked`
- **THEN** скилл появляется в дереве скиллов, отчёт ставится в очередь сборки, доступ к нему имеют автор и администратор
