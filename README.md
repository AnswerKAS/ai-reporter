# AI Reporter

Веб-система формирования отчётности из датасетов. Отчёт — **декларация**:
что показать, а не как посчитать. Пользователь собирает его в конструкторе
мышью или описывает словами; SQL по декларации собирает построитель запросов,
опираясь на общий словарь метрик и разрезов.

```
датасеты ──▶ словарь (метрики, разрезы, связи) ──▶ декларация отчёта
                                                          │
                             построитель SQL ──▶ источник ▼
                             FastAPI + PostgreSQL ◀── React (Vite)
```

Ключевое свойство: **данные всегда живые** — `GET /api/reports/{slug}` при
каждом обращении заново исполняет определение отчёта (SQL к ClickHouse,
PostgreSQL или Oracle). Изменения в источнике видны на странице сразу; логика отчёта
(секции, поля, фильтры) правится в конструкторе и сохраняется как данные —
её можно версионировать, диффать и читать глазами.

Кода в отчёте нет ни на входе, ни на выходе: пользователь SQL не пишет,
модель его тоже не пишет. SQL источника заводит администратор — выражения
метрик и запрос датасета; это граница доверия системы. Текст запроса
проверяется на «один оператор, только чтение», но это страховка от опечатки,
а не защита: для источников датасетов заводите read-only пользователя.

## Структура

```
frontend/                  React 19 + Vite + TS (react-router-dom, recharts, Tailwind v4)
backend/
  app/
    main.py                FastAPI: auth, отчёты, датасеты, словарь, админка
    core/                  config.py (.env), database.py (PostgreSQL), security.py
    schemas/               Pydantic-контракты: report, definition, dataset, semantic, user
    api/                   роутеры: auth, reports, datasets, semantic, admin
    semantic/registry.py   словарь: метрики, разрезы, связи датасетов
    query/                 builder.py (декларация → SQL), dialects.py,
                           interpret.py + phrase.py (словесное ТЗ → декларация)
    reports/executor.py    исполнение определения → ReportSpec
    reports/warehouse.py   демо-витрина ClickHouse + seed
    datasets/              реестр датасетов и адаптеры (clickhouse, postgres, oracle, csv)
    services/storage.py    фасад хранилища артефактов (CSV-файлы)
  artifacts/datasets/      загруженные CSV
```

## Запуск в Docker

Требования: Docker с Compose v2.24+. PostgreSQL для метабазы поднимается
вместе с приложением — ставить его отдельно не нужно.

```bash
cp backend/.env.example backend/.env    # проверьте DB_CONNECTIONS и пароль метабазы
docker compose up -d --build            # http://localhost:8080
```

| Сервис | Что делает |
|---|---|
| `postgres` | метабаза приложения, данные в томе `pgdata` |
| `backend` | FastAPI на :8000 внутри сети; схема и администратор создаются при первом старте |
| `frontend` | nginx: собранный фронт и прокси `/api` → `backend` — наружу торчит только он |
| `clickhouse` | демо-витрина, только с `--profile demo` |

Из `backend/.env` приложение берёт `DB_CONNECTIONS` для метабазы и источников;
`ARTIFACTS_DIR` Compose задаёт сам. Загруженные CSV лежат
в томе `artifacts`. Порт и пароль метабазы меняются переменными окружения
или файлом `.env` в корне репозитория: `APP_PORT` (по умолчанию `8080`)
и `POSTGRES_PASSWORD`. Ключ модели в контейнер из файла opencode не попадёт —
задайте `OPENROUTER_API_KEY` в `backend/.env`.
Если меняете `POSTGRES_PASSWORD`, укажите тот же пароль в
`DB_CONNECTIONS.metabase.dsn`: первая переменная нужна контейнеру PostgreSQL
для создания базы, вторая — приложению для подключения.

Демо-витрина с тестовыми данными:

```bash
# в backend/.env ключ demo уже включён в DB_CONNECTIONS из примера
docker compose --profile demo up -d --build
docker compose exec backend python -m app.reports.seed    # 30 дней данных
```

Что ещё пригодится:

```bash
docker compose logs -f backend          # логи бэкенда
docker compose up -d --build            # пересобрать после обновления кода
docker compose down                     # остановить; данные в томах сохраняются
docker compose down -v                  # остановить и удалить тома (метабаза и CSV пропадут)
```

Чтобы работать с внешним PostgreSQL, уберите из `docker-compose.yml` сервис
`postgres` и его `depends_on` у бэкенда, затем укажите внешний адрес в
`DB_CONNECTIONS.metabase`. Адрес `localhost` там
указывает на сам контейнер, а не на ваш компьютер; до базы на хосте
достучитесь через `host.docker.internal`.

## Локальный запуск без Docker

Требования: Python 3.12, Node.js, доступ к PostgreSQL (метабаза приложения).

```bash
# backend
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env        # настройте DB_CONNECTIONS для метабазы и витрины

# опционально: демо-витрина с тестовыми данными (30 дней)
.venv/bin/python -m app.reports.seed

# запустить
.venv/bin/uvicorn app.main:app --port 8000

# frontend (второй терминал)
cd frontend
npm install
npm run dev                 # http://localhost:5173 (/api проксируется в :8000)
```

При первом старте создаётся администратор **admin / admin** — смените пароль
в кабинете (`/account`, вкладка «Безопасность»). Там же — свои отчёты с поиском
и свод рассылок по всем отчётам сразу.

Отчёты ищутся каталогом: `GET /api/reports` принимает поиск, фильтры (группа
доступа, автор, тема, статус, избранное), порядок и страницу и отдаёт её вместе
с общим числом; `GET /api/reports/facets` — те же разрезы со счётчиками. Левое
меню на этом и построено: закреплённые и недавние сверху, поиск, фильтры и
группировка — списка из десяти тысяч отчётов на клиенте не бывает.

## Конфигурация (`backend/.env`)

| Переменная | Назначение |
|---|---|
| `DB_CONNECTIONS` | JSON всех подключений БД: обязательный `metabase`, необязательный `demo` и именованные источники. У источника `title` — уникальное понятное имя для выбора в форме; `source` и `dsn` задают тип и адрес, при необходимости добавляются `schema`, `sslmode`, `secure`. Для старых записей без `title` временно используется ключ подключения. Для старой установки: `cd backend && .venv/bin/python -m app.datasets.migrate_connections`, затем перезапуск. |
| `OPENROUTER_API_KEY`, `INTERPRET_MODEL` | разбор словесного ТЗ моделью (по умолчанию `deepseek/deepseek-v4-flash`); без ключа разбирает встроенный парсер |
| `CHAT_MODEL`, `CHAT_FALLBACK_MODEL`, `CHAT_TIMEOUT` | диалог о будущем отчёте в конструкторе: модели и предел ожидания (умолчания — `deepseek/deepseek-v4-flash`, `z-ai/glm-5.3-flash`, 90 с) |
| `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL` | необязательные трейсы агентских диалогов; локальный запуск описан в `langfuse/README.md` |
| `ARTIFACTS_DIR`, `ARTIFACTS_STORAGE` | каталог и режим хранилища загруженных CSV |
| `CORS_ORIGINS`, `SESSION_TTL_DAYS` | источники фронта и срок жизни сессии |

## Как собирается отчёт

1. **Датасеты** (`/datasets`) — именованные источники: ClickHouse, PostgreSQL,
   Oracle (12.2+, драйвер в thin-режиме — Instant Client не нужен) или
   загруженный CSV. Схема полей вычитывается из источника вместе с
   комментариями колонок. Источником может быть таблица (в том числе
   представление или матвью) либо **вставленный SQL-запрос** — тогда
   построитель подставляет его подзапросом, не создавая в источнике никаких
   объектов. Такой запрос исполняется на каждую секцию отчёта, на каждый
   список значений фильтра и на детализацию, поэтому тяжёлую агрегацию лучше
   вынести в представление источника и завести датасет на нём. Строка
   подключения задаётся ключом из `DB_CONNECTIONS`. В админке новый датасет
   заводят выбором подключения и SQL-запросом; внутренний slug создаётся из
   названия автоматически. Ранее заведённые датасеты на таблицах и CSV
   продолжают работать. Админка находится по адресу `/admin?tab=datasets`,
   а `/datasets` — каталог: список сужается поиском
   (название, slug, таблица, имена полей) и фильтрами по источнику и статусу
   подключения — и того и другого можно выбрать несколько сразу; выбранное
   остаётся в адресе (`?source=postgres,csv&status=error`), так что ссылкой на
   выборку можно поделиться. Карточка открывает окно с вкладками: превью
   (с сортировкой и фильтрами по колонкам), поля датасета, показатели,
   разрезы и диалог вопросов по данным, а администратору — ещё черновик словаря и правка SQL-запроса.
2. **Модель данных** (`/model`, админ) — словарь: метрика («Выручка» =
   `sum(revenue)`), разрез («Город» = `region`) и связи между датасетами.
   Выражение метрики проверяется на источнике сразу: битая метрика получает
   статус `error` и в отчёт не проходит. По вычитанной схеме датасета система
   предлагает черновик словаря — разрезы из строк и дат, показатели из чисел;
   администратор отмечает галочками, что завести.
3. **Конструктор** (`/builder`) — два шага: выбор данных (датасеты,
   показатели, разрезы, свои поля из колонок и формулы) и раскладка секций
   (KPI, график, таблица) перетаскиванием или кликом. Рядом — живой
   предпросмотр по реальным данным.
4. **Отчёт** (`/reports/<slug>`) — читатель применяет фильтры, данные
   пересчитываются сразу; страница обновляется, пока открыта.

Описание словами (`«выручка и заказы по городам топ-15 столбцами»`)
превращается в ту же декларацию: модель выбирает имена **только из словаря**,
числа не видит и не производит, а без ключа модели разбор делает
детерминированный парсер.

## Права

- любой авторизованный: просмотр датасетов и словаря, конструктор,
  предпросмотр, свои отчёты, фильтры, правка названия/описания;
- администратор: датасеты, метрики/разрезы/связи, создание и удаление
  отчётов, сохранение определения, пользователи, группы и назначения доступа.
