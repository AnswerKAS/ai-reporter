# Тесты бэкенда

```bash
cd backend
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest              # весь набор, ~12 секунд
.venv/bin/python -m pytest tests/test_builder.py -q
.venv/bin/python -m pytest -k "фильтр"  # имена тестов русские, поиск по смыслу
```

## Чего тесты не делают

Ни одного обращения наружу: ни к PostgreSQL-метабазе, ни к источникам данных,
ни к SMTP, ни к модели. Набор целиком гоняется на пустой машине и не зависит от
`.env`.

- **Метабаза** — `fakedb.py`: SQLite в памяти под контрактом psycopg-соединения.
  Приложение выполняет **свои настоящие SQL-тексты** (включая `init_db()` и
  миграции), различия диалектов закрывает переписывание запросов — ровно
  столько, сколько приложение действительно использует: `%s`, `IS NOT DISTINCT
  FROM`, `ADD COLUMN IF NOT EXISTS`, `= ANY(%s)`, `information_schema.columns`.
- **Источники данных** — `fakesource.py`: адаптер с тем же интерфейсом, что у
  ClickHouse/PostgreSQL/Oracle. Он запоминает каждый выполненный SQL — по нему
  тесты и проверяют, что именно собрал построитель, — и умеет ломаться так, как
  ломается живой источник (недоступен целиком, падает на конкретном выражении).
- **Почта** — подменяется `sender.send` или сам `smtplib`.
- **Модель** — фикстура `no_llm` (autouse) снимает ключ OpenRouter, поэтому
  разбор описания идёт детерминированным парсером. Путь через модель проверяется
  отдельно с подменой `_ask`.

## Как устроено

| Файл | О чём |
| --- | --- |
| `test_routes.py` | опись всех методов API: новый эндпоинт без тестов роняет набор |
| `test_api_*.py` | HTTP-контракт каждого метода: успех, права, 404/409/422/502 |
| `test_builder*.py` | сборка SQL: секция, фильтры, джойны, предагрегация, детализация |
| `test_executor.py`, `test_drilldown.py` | декларация → ReportSpec и сырые строки |
| `test_dialects.py`, `test_sqlsource.py`, `test_adapters.py` | различия источников |
| `test_phrase.py`, `test_interpret.py` | словесное ТЗ → декларация |
| `test_database.py`, `test_*_registry.py` | хранилище и словарь |
| `test_render.py`, `test_mail_*.py`, `test_worker.py` | файлы отчёта и рассылка |

## xfail — это найденные дефекты

Тесты, помеченные `@pytest.mark.xfail(strict=True)`, описывают **правильное**
поведение и падают, потому что код ведёт себя иначе. Причина дефекта и способ
починки — в `reason`. Когда дефект исправят, такой тест начнёт проходить, и
`strict=True` сообщит об этом (XPASS = провал): маркер надо снять.

Рядом с каждым лежит характеризующий тест, фиксирующий поведение как оно есть
сейчас, — чтобы правка не прошла незамеченной.
